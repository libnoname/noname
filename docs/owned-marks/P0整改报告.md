## 2. 新接口为什么未覆盖旧技能

原兼容桥仅在桶已启用时把旧 add 记为 anonymous，旧 remove 是聚合扣减，has/count 看聚合值。它维护的是数量一致性，没有调用者管理权。

本轮让旧 API 通过**同一账本后端**接入：显式注册策略、执行者上下文可靠且技能范围匹配时，旧 add 创建 owner 份额，旧 has/count 可以按该规则查询本来源，旧 remove/clear 精确消费本来源。不再要求该类原始函数逐行替换 API。测试中的原始徐荣和协穆因此能够运行。

但这不是“零声明”的自动兼容：源码没有提供语义时，系统不能知道该数值是资源、共享资格、外部归属还是 HP 阈值。策略只做规则声明，不把技能 ID 当玩家身份；actor 始终是明确的 Player 实例。**产品默认没有批量注册这些实验规则**，未声明技能不会突然私有化。

## 3. 底层实现与原接口语义

详细设计和签名见 [p0-design.md](p0-design.md)。关键入口：

- `game/markCompatibility.js`：注册／验证／恢复 JSON 策略，管理同步执行作用域，选择旧 API 的查询和消费权限。
- `player.js`：旧 add/remove/clear/set/count/has 的可选桥接；没有策略时保留原行为；显式 owner/all 操作不依赖环境推断。
- `library/index.js`：触发和主动 filter 使用显式 player+skill。
- `content.ts`、`gameEvent.ts`、`player.js`：引擎建立 cost/content、主动技能、初始化、移除及目标选择回调时绑定已知执行者。
- `GameEvent/compilers/ArrayCompiler.ts`：旧 step 和 async 的统一调用入口，每次进入原函数时使用事件的显式绑定。
- `game/ownedMarks.js`：策略与账本一同恢复，非法策略整体拒绝，无策略旧快照清除旧规则，投影和恢复不重新消费标记。

查询默认保持总数；只有匹配已声明规则的执行上下文才可能采用 owner 视角。`{scope:'all'}` 强制合计，`{scope:'owner',owner}` 明确指定来源。remove/clear 同样有这两个显式范围；策略可声明全来源清理。未知私有删除只动匿名份额，不让旧调用错误清掉已知 owner。

共享和自身资源仍走原聚合逻辑；数组／对象不能被数值策略强转。受声明保护的有符号旧数值 add/remove 保持增减算术含义，但这不意味着引擎自动理解阈值含义。

## 4. 哪些来源可靠，哪些不可靠

**已经有明确入口的情形：** 技能 filter、主动使用、技能 init/onremove、绑定过的旧 step 每一步、async 函数首次 await 之前、由引擎创建时捕获上下文的目标选择回调。filter 的 player 是持有者，event.player 可能是受害者；本轮没有把两者混用。

**不能直接推出来源的情形：** 原始裸 API、未绑定直接调用、未绑定计时器／Promise 回调、async 首次 await 后、委托其他玩家创建的效果、全局 mod 的多个 provider、任意 storage/数组参数写入、没有转移契约的 remove+add。

同步栈遇到返回 Promise 立即退出。不能把 actor 放进全局变量并 await 完整函数：等待期间其他任务会被错误认主。显式事件 metadata 只能证明事件的执行者，不能让浏览器自动拥有 async-local 能力。全局和直接 mod 入口使用 null 屏蔽外层技能身份；不会取 globalmap 的第一名作为 owner。

## 6. 原始双神甘宁与其他代表：仍未通过的断言

原始协穆另验证同一套声明接口可隔离目标、原收益函数和过期清理；这是测试采用的来源语义，不把原共享文本伪称为 bug。原始梦魇、傀、暴怒、忍戒做共享／自身资源对照，保持聚合逻辑。傀的实验私有化测试只作机械适配诊断，不是推荐产品规则。

## 7. 无损自动推断不可能的最小反例

**裸调用不可区分：** 两次都只观察到 C.addMark('m',1)，可能是C代A施加，也可能代B施加；输入完全相同，正确 owner 不同。任何只看该调用的函数必然至少错一个。补上 event.player=C 也不增加委托来源信息。

**转移意图不可区分：** `C.removeMark('m',1); D.addMark('m',1)`，可能转移原效果，也可能销毁后新建。二者要求不同的 effect ID、creator 和期限，但调用轨迹一样。只关联调用时间并不能证明意图。

**参数配对不可恢复：** 来源集合[A,B]、花色并集[红桃,梅花]，既可能 A→红桃/B→梅花，也可能相反。两个聚合集合完全一样，匹配花色的收益者却不同。焰狱的原两个集合不能无损恢复二分关系。

**规则语义不可恢复：** addMark(4) 可能是4个资源，也可能是HP阈值4或持续4回合。相同参数不携带单位。把它们统一当4份效果同样可能错误。

这些反例不证明“任何零武将源码改动方案都不可能”：集中规则声明可以补足信息，甚至集中替换所有技能函数也能改变行为。但后者只是把逐技能补丁搬地方，不是需要的自动推导。真正可维护的方向是有限种通用策略和必要的最小显式元数据。
