# 武将扩展包增量整理（中文使用说明）

整理器读取 `扩展包/武将扩展`，在 `扩展包/整理结果` 生成多个可分别导入的 ZIP。它不修改原压缩包，不向主程序安装扩展，也不操作游戏存档。

## 使用

按照 [启动文档](how-to-start.md) 安装项目所需的 Node.js、pnpm 后，在项目根目录打开终端：

```powershell
pnpm install --frozen-lockfile
pnpm extensions:organize
```

之后向 `扩展包/武将扩展` 新增、修改或删除压缩包，再执行同一条命令即可。也会递归扫描该目录的子文件夹。

```text
扩展包/
├─ 武将扩展/                  原始输入，可以手动增删
├─ 已安装扩展/                不参与本次整理
└─ 整理结果/
   ├─ 整理报告.md             中文结果，按扩展名列出 ZIP 下载链接
   ├─ report.json             原因、保留数量、剔除的武将 ID
   ├─ manifest.json           当前有效来源、首次发现顺序、输出和武将归属
   ├─ packages/               本次有效的规范化扩展 ZIP
   └─ .cache/                 分析缓存、二次压缩的内层 ZIP
```

ZIP 文件采用内容指纹命名。请从 `整理报告.md` 根据扩展名选取文件，避免凭指纹猜测名称。报告里的“成功”指结构与支持范围内的静态检查通过，不表示已经逐个完成游戏对局测试。

在游戏中通过“扩展 → 获取扩展 → 导入扩展”选择报告链接对应的 ZIP；导入后按游戏提示重启。整理器不保证与目录之外的扩展（包括已安装扩展）的武将和技能不冲突。首次试用建议使用单独测试存档，先逐个启用确认。

## 预览与完整核验

```powershell
# 只预览：不更新正式输出、索引和报告；临时缓存会清理
pnpm extensions:organize --dry-run

# 重新计算全部输入哈希、分析代码，并核验已有输出哈希
pnpm extensions:organize --verify

# 指定其他输入和输出，不影响默认整理目录
pnpm extensions:organize --input "D:\素材\武将扩展" --output "D:\素材\整理结果"

# 查看参数
pnpm extensions:organize --help
```

输入和输出不能相同或相互嵌套，输入目录的符号链接也不接受。一次只允许一个进程修改同一个输出目录。

普通运行使用文件大小、修改时间作为快速判断，仅对新增或变化的输入计算 SHA-256。文件内容改变但大小、修改时间都被保留时，必须使用 `--verify`；普通扫描不能发现这种特殊变化。预览使用独立临时缓存，会比普通增量运行慢。

## 武将的保留顺序

1. 首次运行按相对文件名的固定字符顺序处理，与 Windows 资源管理器的中文排序不一定相同。
2. 同一个原包中拆出的扩展按真实内部路径段的固定顺序处理；根目录入口使用空路径，先于内嵌 ZIP，不使用“根目录”这段显示文字排序。
3. 首次发现顺序写入索引。新增包即使名称排在前面，也排在已发现来源之后。
4. 武将使用完整内部 ID 精确比较，保留第一个能够成功输出的来源；大小写、前后空格均不擅自修改。同显示名称、不同 ID 不会合并。
5. 后续包中的重复武将从定义和支持的分类、替换、翻译等元数据中剔除；其他武将不能依赖被剔除的武将才能运行。

例如 A 包有“甲”，B 包有“甲、乙”。整理后 A 保留“甲”，B 只保留“乙”。B 可以单独导入，但不会提供“甲”。如果 B 的“乙”需要变身成“甲”，程序会跳过 B 并报告引用问题。

删除 A 的原压缩包并重新运行后，A 的有效记录与输出会移除，B 会重新生成并恢复“甲、乙”。删除的是完全重复压缩包的一份副本时，只要另一份还在，就继续保留原输出。同一次扫描内的重命名可通过内容哈希识别并保持优先顺序；先删除并运行、以后再添加则作为新发现来源。

修改已有压缩包会保留该来源的首次发现顺序，并重新检查受影响的输出。失败或跳过的扩展不占用武将归属。全部武将均重复或本身没有武将的包不输出；这类包若另有卡牌/模式功能，报告会提醒人工处理。

不要单独删除 `manifest.json`：它保存“谁先出现”的历史。丢失索引后应选择新的空输出目录重新整理，此时优先顺序会重新按文件名建立。

## 支持的格式与跳过原因

支持 ZIP 根目录入口、多套一层或多层普通目录、最多三层内嵌 ZIP、多个互不嵌套的扩展根目录。拆分时各包保持自己的文件布局；外层许可证、README 等文本文件会附带到 `_organizer_source`。

一个包同时有直接入口和内嵌 ZIP 时，两者都检查并记录。存在相互嵌套、不能安全拆分的入口时，也会继续检查其内嵌 ZIP。外层来源文档按原始字节保留。

2026-09-09 的全量复查结果和修复说明见 [复查记录](extension-organizer-audit.md)。

当前自动适配这些入口：

- `game.import("extension", function (...) { return { ... }; })`，工厂直接返回扩展对象。
- `game.import("extension", { ... })`。
- 简单 ESM：标准主程序导入、`export const type = "extension"` 和直接导出对象/仅返回对象的默认工厂。
- `package.character.character` 中直接声明的武将，以及直接声明的技能字典。
- 额外 `package.js` 若只有 `extension["扩展名"] = { ...静态元数据... }`，验证后可以保留。

以下情况会给出具体原因，整个相关子扩展跳过，不生成部分损坏的包：

- 跨文件模块、额外脚本/网页、动态顶层初始化、运行时注册武将或修改全局技能等超出当前适配范围。
- 武将或技能定义使用展开、计算属性、无法追踪的变量，或语法本身不正确。
- 缺入口、只有 TS 源工程、加密包、无法可靠解码、压缩包损坏。
- 同内部扩展名冲突：主程序按该名称安装，会发生替换；程序不冒险自动改名。
- 同技能 ID 的实现不同，或剔除后留下静态武将引用/无法确认安全的动态武将表访问。
- 明确引用其他扩展的资源，或可识别的显式自身资源路径缺失。

“暂不支持”不代表原包一定坏了。它表示该包不能由现有适配器可靠地自动整理；可以根据报告为具体结构扩展适配器。纯素材、补丁、说明文档不会自动伪装成扩展。

## 去重、性能与可靠性边界

完全相同的源 ZIP 使用 SHA-256 识别，只输出一份，并关联所有来源。已有分析缓存可以复用；只有归属或内容发生变化的输出才重新压缩。媒体文件使用存储方式写入 ZIP，文本使用压缩；按需流式读取资源，避免一次将大包全部解压到内存。目前逐包处理，优先限制内存和磁盘争用；不启动无限并发任务。

独立安装所需的共享技能、图片和配音保守保留。不同包都需要的相同资源仍各自携带，不能简单按内容哈希删除其中一份。当前不做跨包资源路径重写，也不按文件名猜测“专属资源”并删除。这意味着实现保证的是武将定义去重及重复原包去重，而非所有输出 ZIP 的资源字节全局唯一。

整理过程不执行下载扩展的 JavaScript。用语法树识别与修改代码，并重新读取生成的 ZIP 验证武将清单。校验包括读取资源时的 CRC/长度检查、目录穿越、Windows 保留名称、大小写冲突、符号链接、加密、文件数量和解压上限。限制为单条目 1 GiB、每个 ZIP 解压总量 4 GiB、最多 100,000 个条目，以及内嵌 ZIP 累计 8 GiB 等。

生成时先写临时 ZIP，再发布正式文件和索引。更新日志 `journal.json` 用于进程中断后的恢复：未提交的新文件清理，已提交的旧文件退役。清理仅针对程序记录的输出文件，不删除源压缩包或输出目录中用户额外放入的文件。源文件在整理中发生增删改时会中止发布，要求重新运行。

缓存是可重建的加速数据，旧来源的分析缓存可能暂时保留，但不再属于有效来源记录，也不会继续输出；不要将缓存当作可安装扩展。发生异常中断后，重新执行命令即可恢复。已结束进程留下的锁会在确认进程不存在后清理；无法确认的锁会提示检查，避免并发破坏。

静态检查不能证明任意第三方技能的实际对局行为正确，也不能完整分析所有动态资源路径或所有跨扩展交互。报告保留此状态，不把未做的实机测试标成通过。

## 开发与 Git

```powershell
pnpm extensions:test
```

测试使用程序生成的小型扩展，覆盖去重、共享技能保留、删除后的候选恢复、增量、重命名、内嵌压缩、多包拆分、冲突、输出修复、CRC 和中断恢复。只有测试自身的合成代码会在测试沙箱里执行。

源码位于 `scripts/extension-organizer/`，命令入口是 `scripts/organizeExtensions.ts`。`package.json`、`pnpm-lock.yaml`、脚本、测试和本说明应纳入版本控制。默认输入、整理结果、缓存和压缩包位于已被 `.gitignore` 忽略的 `扩展包/` 下，无需提交。整理命令不会自动执行 Git 提交或推送。
